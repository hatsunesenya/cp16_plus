# 追加调查：实拍时"一个字都不显示"的真正原因

> 本文件接《非整十秒接收-调研与方案.md》。你反馈："不是开头几秒空白，播放到结束都没有字，
> 但原始瀑布图里字迹完全可辨"，并且截图里存档区显示 `20–30 s 4 字 / 30–40 s 6 字 / 40–50 s 8 字`。

## 一、先排除的两件事

1. **解码器在 48 kHz 下没问题**。新增单元测试 `decodes_at_48k`：
   用发射器在 48 kHz 生成信号 → 走 `Stream::new(48000)` 抽取到 8 kHz → 解调，
   断言 `cells > 0`，测试通过。
2. **中途加入本身是可行的**。把 25 字示例从 3 s / 8 s 处截断后回放，分别解出 10 / 13 个字
   （完整版 14 个），说明"没有开头报文头"并不致命。

## 二、真正的原因：主界面的峰值基准被"启动爆音"带偏

你截图里的关键线索是**存档区有字数（4/6/8 字）**——这说明字符已经解出来了，
只是**主界面把它们画成了黑色**。查渲染代码：

```js
// 旧代码
let mx = 0;
for (const v of row) if (v > mx) mx = v;
S.peak = Math.max(mx, S.peak * 0.9995);   // ← 问题 1：衰减极慢（≈2000 行才降 10 dB）
const lo = -(22 + (14 - S.gain));         // ← 问题 2：滑杆往右反而变窄
```

- 声卡/设备一打开常有一声"咔"（满幅瞬态）。它成为 `S.peak` 之后，**以 0.9995/行 的速度衰减，
  50 行/秒下要 40 秒才降 10 dB**。而真正有字的那几行比爆音低 60–80 dB，
  归一化后全部落到 `t = 0` → 背景色 → 整屏全黑。
- WAV 回放没有这个瞬态（文件本身就是干净的），所以回放一直正常——这也是我上一轮
  测不出来、误判成"切行问题"的原因。
- 对比度映射 `22 + (14 - gain)` 在 gain 调大时反而收窄，也没法救。

## 三、已修（本轮）

1. **峰值基准改为分位数起算**：先攒 24 行的行极大值，取 90% 分位作为参考
   （一声爆音只占 1/24，落在分位之外），之后按 2%/行 跟随。
2. **对比度改为单调**：`lo = -(8 + S.gain)`，滑杆 0→60 对应 8→68 dB 动态范围，
   默认 14 = 原来的 −22 dB，行为不变，往右能看见更弱的内容。
3. **回归测试** `peakAnchor`：注入"一行满幅爆音 + 40 行弱字"，断言最后一行渲染亮度 > 40
   （即不是全黑）。自检结果：`tabs|settings|qso|freq|rawRoute|rawPush|peakAnchor|rawHover|rawParams` 全 ok。

另外修掉了你指出的**行率不生效**：`raw_hop` 原来在 pump 启动时只算一次，
现在每帧按当前 fps 现算。实测 50 帧/秒 → 3 秒收 147 帧；400 帧/秒 → 1191 帧。

## 四、还剩下的那个真问题（需要你确认是否做）

修完渲染后，**中途开始接收仍会丢开头几个字**，因为切行要等：

- 一个 BCON 突发（每 8 字一次，最多等 ~1 个字符周期），或
- 一个同步帧（每 10 秒一次，仅在没有突发时才开"盲锁段"）。

实测从 3 s 处开始 → 解出 10/14 字（丢 4 个），从 8 s 处 → 13/14。
这与"完全没字"是两回事，但确实存在。

对策仍是上一份文档里的三条：**B（同步帧快捕获）→ C（手动档位）→ A（免突发探索段）**。
若希望"从一开始就一个字不少"，建议至少做 B + C；A 是根治但工作量大。

## 五、给你的两个动作

1. 装上本轮版本，再用外部设备播一遍 25 字示例——应该能直接看到字（不再全黑）。
2. 若仍有丢字（开头几个），告诉我丢几个，我按 B+C 做，把首字延迟压到 1–2 秒内。

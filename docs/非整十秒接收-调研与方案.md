# 非整十秒开始接收时的字符显示：调研与方案

> 现象：用外部设备在**非整十秒**的时刻开始播放 CP16+ 音频（或从中途开始接收），
> 主界面不出现任何字符。即使没有开头那帧报文头，人眼仍然能从瀑布里读出中间的字，
> 界面却不给任何提示。
>
> 本文只做调研与方案，不改代码。

## 一、现在的机制

1. 音频进来后，先由双导频（450 / 1250 Hz）解出频率标定 `est`，并持续维护。
2. **切行（解调）只发生在"段"里**。段（`Seg`）只有两种开法（`rust/crates/core/src/rt.rs`）：
   - **按突发**：每确认一个控制信道突发（HDR / BCON），就以"突发起点 + (符号数+15) 个符号"作为第一行起点开段（`rt.rs:711-728`；
     HDR = 203 符号，BCON = 100 符号）。
   - **盲锁段**：没有任何可用突发、但**已收到同步帧**时，从同步帧结束处开段（`rt.rs:682-706`）。
3. 段内按 `t_row`（= k/Δf，档位决定）逐行解调，再用边距音找字符边界（`emit_cells`）。
4. 档位（栅格 / k / R）来自 HDR 或同步帧；两者都没有时用默认档位。

**关键点：没有突发、也没有同步帧，就永远不会开段 —— 画面一片空白，不是"读不出字"，而是"没在切行"。**

## 二、实测：中途开始到底会发生什么

用发行包里的 `示例-长报文25字.wav`，在不同位置截断后送进引擎（WAV 回放走的是同一条流水线）：

| 起点 | 音频时长 | 解出字符数 | 收到同步帧 | 报文头 |
|---|---|---|---|---|
| 0 s（完整） | 38.9 s | 14 | 3 | BG1ABC / OM89AB |
| 3 s（切掉开头） | 35.9 s | 10 | 2 | 无 |
| 8 s（切掉开头） | 30.9 s | 13 | 3 | 无 |

结论：**接收端本身是能"中途加入"的**，但依赖两件事——
1. 音频里还有 **BCON 突发**（每 8 个字符一次）或**同步帧**（每 10 秒一次）；
2. 等到它们出现为止。BCON 最多等 ~1 个字符周期，同步帧最坏等 **10 秒**。

所以"完全没有字"的情形基本是这三类：
- **发射端只发 HDR + 字形**，中途没有任何突发和同步帧（某些实现/手工录音）→ 永远不开段；
- 刚开始接收的头几秒（尤其录音短于 10 s）→ 还没等到第一个同步帧；
- 声卡/设备刚打开时前若干百毫秒的音频被丢掉，恰好把唯一的突发吞掉。

## 三、候选方案

### 方案 A：不等突发，导频在就开"探索段"（推荐，最小改动）

只要 `est`（导频标定）可用、且缓冲区里有 ≥2 行音频，就开一个段：

- 栅格（档位）未知时，按候选集 `{M2, M4, M8}` × `{16 音, 24 音}` 逐个试，
  用**行周期自相关**（16 个音的总能量序列在 `t_row` 上的周期性）和**边距音对比度**打分，取最高者；
- 行相位再在 `[0, t_row)` 内做 N 点（建议 8–16 点）搜索，取边距音最锐利的相位。

改点：`rt.rs` 的 `scan()` 里加一条"无突发也能开段"的分支（约 60–100 行），
外加一个"栅格搜索"小模块。风险：误开段会显示垃圾行；用打分阈值 + 置信度显示（`conf` 低时界面标注）控制。

**收益**：从"等到 10 秒"变成"1–2 秒内出字"，且对不发射突发的源也有效。

### 方案 B：同步帧快速捕获（最省事）

现在同步帧只在扫描窗口里搜（`SYNC_COAST_WIN` 等）。改为：**会话开始后的前 2 秒全段搜一次**，
把"首个同步帧"的等待从最坏 10 s 降到 <1 s。约 20–40 行改动，无行为风险。

**收益**：缓解"开头几秒空白"，但仍然依赖对方发同步帧。

### 方案 C：手动指定档位（兜底，最直观）

界面上加"强制档位 / 强制行定时"（默认关）。用户在频率上听到对方用 M4 时，
直接选 M4，接收端立刻按 M4 开段并切行，不再等任何突发/同步帧。

改动主要是 UI + 一个 `force_mode` 参数（`Stream::new(fs, force_mode)` 已经支持这个形参，
现在传的是 `None`，把它接到设置里即可）。约 30 行。

**收益**：对"对方只发字形"这类源，是最可靠的兜底；也让调试/手工录音回放可控。

### 方案 D：点阵直读（不做字符边界，只给"看"）

不做行切分与字符边界，把能量矩阵按 16×16 滑窗直接渲染/给用户看（相当于原始瀑布上叠一个可拖动的字形网格）。
保留现有原始瀑布即可覆盖大部分需求，成本中等、收益偏体验。

## 四、建议的落地顺序

1. **B**（同步帧快捕获）——改动最小，先把"开头几秒空白"消掉；
2. **C**（手动档位）——30 行，给出确定的兜底手段；
3. **A**（探索段 + 栅格/相位搜索）——把"无突发也能出字"补齐，这是根治；
4. **D** 视需要再做（界面层）。

## 五、验收方式

| 用例 | 期望 |
|---|---|
| 完整音频（0 s 起） | 与现在一致（14 字左右），不回归 |
| 从 3 s / 8 s 起 | 1–2 秒内开始出字（B+C 后应 <2 s） |
| 只含 HDR + 字形、无 BCON/同步帧 | 选强制档位后能出字（C）；开启探索段后无需选择（A） |
| 纯噪声 | 不出字、不出垃圾行（打分阈值生效） |
| 档位猜错 | 画面标注"降级/低置信"，不崩 |

## 六、需要你决定

- 是否按 **B → C → A** 的顺序做？还是先做 A（工作量最大但最根治）？
- 界面上的"强制档位"放在「设置 → 接收」还是主界面接收栏？（我倾向设置里，避免主界面变复杂）
- 低置信度时，字符仍然显示但标灰？还是干脆不显示只给提示？

# 回放能出字、实时不行：差异究竟在哪里；以及这个协议到底该怎么做

> 这轮只做分析，不改代码。对象是你提的两个更基本的问题。

## 问题一：同一条通路，为什么回放能出字、实时不行

先说清楚"共用"到底共用在哪。确实是同一个 `Stream`、同一套解调、同一个 `run_pump`，
但**送进 `Stream` 之前的每一段都不一样**：

| 环节 | WAV 回放（`/api/decode`） | 实时采集（声卡） | 是否已排除 |
|---|---|---|---|
| 采样率 | 软件重采样到 **8000**，`Stream::new(8000)` **不抽取** | 设备原生 **48000**，`Stream::new(48000)` 走 97 阶 FIR 抽取 | **已排除**：单元测试 `decodes_at_48k` 用 48 kHz 生成信号，抽取后能正常出字 |
| 声道 | 单声道（文件本身） | **双声道 → 程序里直接平均 L/R** | **未排除，高嫌疑**（见下） |
| 块大小/时序 | 固定 20 ms，软件 sleep 定速，**永不丢块** | 设备回调长度不定，经 mpsc 通道送泵 | 未排除（若积压会迟到但不丢） |
| 电平/直流 | 文件里是什么就是什么 | 麦克风增益、**直流偏置**（你数据里 DC 处 +6 dB）、可能削顶 | 未排除 |
| 系统音频处理 | 无 | Realtek 驱动常默认开 **AEC / 降噪 / AGC** | **未排除，高嫌疑** |
| 声学 | 无 | 房间混响、扬声器-麦克风频响、距离变化 | 未排除 |
| 起始条件 | 从报文头开始 | 常常从中途开始 | 已知（会影响字数，但不至于 0） |
| 频标定 | — | 上一轮已修，现在 a≈1.0000、conf 0.83–0.95 | **已排除** |

### 两个高嫌疑项，都能单独解释"回放好、实时差"

**1. 双声道直接取平均，可能形成梳状滤波**

```rust
// rust/crates/audio/src/lib.rs
for frame in data.chunks(ch) {
    mono.push(frame.iter().sum::<f32>() / ch as f32);   // L+R 平均
}
```

如果两路麦克风（或阵列的两个振膜）之间有距离 Δ，平均后会在
`f = c/(2Δ)` 的奇次倍处产生深零点。Δ = 6 cm → 第一个零点就在 **2.8 kHz**；
Δ = 12 cm → 1.4 kHz；振膜间距再加外壳声学路径，零点完全可以落进 **800–1200 Hz 的字形带**。
一旦落进去，某些音被挖掉 15–20 dB，判决必然乱，而**瀑布图仍然看得见**（人眼靠上下文补）。

→ 好消息：这条**不需要改协议**，取单声道或做时延对齐即可。

**2. Windows/驱动的 AEC、降噪、AGC**

这三项对 CP16+ 是**结构性破坏**：降噪做的是谱减法（会把 25 Hz 间隔的窄音当成噪声削掉），
AGC 会把"有音/无音"的对比压平，AEC 甚至会把播放的声音当回声消除（如果你用扬声器外放）。
Realtek 的"麦克风增强"默认常常是开的，而设备名里就带 `Realtek(R) Audio`。

→ 这条也不需要改协议：关掉增强，或改用线路输入。

### 所以"共用通路"这个说法要修正

我们共用的是**解码器**，不是**输入链**。回放测试证明的是"解码算法在干净信号上能工作"，
它从来没有验证过"设备+驱动+声学"这一段。你现在的实时数据（cells 10–20、频谱平坦、
DC 占优）恰好是"输入链在破坏信号"的典型指纹。

### 一次就能定性的实验（不改代码）

用你已有的 `m4_snrm6_M2.wav`，三种输入各跑一遍，对比 `cells`：

| 输入方式 | 怎么做 | 预期 |
|---|---|---|
| A 文件回放 | 拖进界面回放 | 已知 ~24 字（基准） |
| B 系统混音 | 声音设置 → 录制 → 显示禁用设备 → 启用「立体声混音」，选它当输入，同时播放 WAV | 若接近 A，说明设备/DSP 是元凶 |
| C 扬声器+麦克风 | 你现在的做法 | 若明显低于 B，说明声学/DSP 在吃信号 |

A→B 的落差 = 设备与驱动 DSP 的代价；B→C 的落差 = 房间声学的代价。
这比继续猜要快得多，而且不需要我改一行代码。

## 问题二：如果自动解码不如人眼，它的意义何在；要完美输入才能用，短波上是不是废的

这个问题问到根子上了，我分三层回答。

### 1. 先说定位：频谱书写的主通道本来就是人眼

协议规范里写得很清楚：**文本只由人眼判读**，机读层（DQPSK 控制信道 + 同步帧）
只承载呼号、网格、档位、参数。"文本必须人眼读"是我们自己定的规则，不是妥协。

在这个定位下：

- 人眼判读是**主业务**，不是兜底；
- 自动解码是**抄收辅助**（记日志、抄错字、远程守听），它的价值是"少写字"，不是"替代眼睛"；
- 因此评价标准不该是"自动解码准不准"，而应该是"**它有没有帮到判读，有没有误导**"。

现在的问题是界面把这层关系搞反了：主界面把自动解码的瀑布放得最大，
反而把"人眼判读"挤成了附属。这是我设计上的偏差，不是协议的问题。

### 2. 短波上到底能不能用：能，但不是现在这种判决方式

给几个具体数字：

- 16 个音跨 **375 Hz**（800–1175），小于短波典型相干带宽（0.3–1 kHz）→ **近乎平坦衰落**，
  不会频率选择性衰落把某些音挖掉；
- 短波的主要敌人是 **QSB（整段电平在几秒内摆动 10–20 dB）** 和 **多径时延 1–3 ms**；
- 我们一行 80 ms，音间隔 25 Hz（理论分辨 12.5 Hz，余量 2 倍）。

结论：**协议在短波上可行，前提是判决必须"逐行相对"而不是"全局绝对"**。

QSB 是整体乘性变化——只要每一行用自己的电平做参考，它就伤不到判决；
而现在的实现用的是跨行的门限，QSB 一来整列翻转。这是工程实现的问题，不是协议天花板。

顺带说：我做的加噪实验（SNR 降到 10 dB 仍有 18 字、0.25 s 混响也是 18 字）
也支持这个判断——**噪声和混响不是主要矛盾，判决方式才是**。

### 3. "必须完美环回才能用"是个误解

环回在我上一版方案里的角色是**测量工具**：用来把"设备/DSP"与"算法"两个变量分开，
而不是产品必须依赖它。产品路线应该是：

- **输入侧**：正常用线路输入或麦克风即可；软件做的应该是"把能控的都控住"
  （单声道、关增强检查、高通去直流、电平表），而不是要求用户搭一个无回声环境；
- **判决侧**：逐行相对 + 软判决 + 用同步帧/BCON 做在线均衡，把 QSB 和频响倾斜吃掉；
- **交互侧**：自动解码给**置信度**，低置信度的字标灰而不是硬写；人眼视图始终是第一等公民。

## 由此得到的优先级（与我上一版方案不同的地方）

1. **先查输入链**（半天，不改协议）：单声道取一路、关 AGC/降噪、去直流、
   加输入电平与削顶指示。这一条很可能就解释了 80% 的差距。
2. **判决改逐行相对**（1–2 天）：每行用完形/空白行估自身噪声，QSB 免疫；
   配合软判决与置信度输出。
3. **界面回归"人眼优先"**（半天）：主界面把判读视图做主角，
   自动解码降级为辅助面板并显示置信度。
4. **在线均衡**（1–2 天，可选）：同步帧/BCON 做信道估计，进一步压频响倾斜。
5. 环回：仅作为诊断开关保留，不作为使用前提。

## 需要你确认的两点

1. 先做 **1（输入链排查）**，还是直接做 **2（判决改逐行相对）**？
   我倾向先做 1——它最便宜，而且能立刻验证"是不是设备在吃信号"。
2. 界面是否接受把"自动解码"降级为辅助面板（人眼判读视图回到主位）？
   这关系到后面所有 UI 改动的方向。

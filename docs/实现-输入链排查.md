# 输入链排查：本轮已实现（B0.1.3）

> 对应《分析-回放与实时的差异及协议定位.md》里的"优先级 1"。
> **界面一行未改**，只动了采集链与状态字段。

## 一、改了什么

### 1. 声道：不再盲目平均 L+R

```rust
// 旧：mono.push(frame.iter().sum::<f32>() / ch as f32);
```

两路有距离时平均值会产生**梳状滤波**，零点可能正好落进 800–1200 Hz 的字形带，
把某些音挖掉 15–20 dB——而瀑布图靠上下文仍"看得见"，所以一直没被发现。

现在的策略（`ChannelMode`）：

| 模式 | 行为 |
|---|---|
| `Auto`（默认） | 前 0.5 秒量两路能量，选更响的一路；之后每 5 秒复查，**只有另一路强 6 dB 以上才切换**（避免来回跳） |
| `Mix` | 旧的 L+R 平均（保留用于对照实验） |
| `Index(0/1)` | 强制用某一路 |

接口：`POST /api/audio?action=start&channel=auto|mix|0|1`（默认 auto）。
单声道设备直通，不受影响。

### 2. 去直流 + 低频隆隆声

一级 ~30 Hz 一阶高通（`DcBlock`）。你现场数据里 DC 处比中位高 60+ dB，
白占动态范围；这一级对 450 Hz 导频的损失 < 0.2%。

上电第一个样点只用来"对齐"（否则设备启动的直流跳变会被整成幅度 2.6 的尖峰，
既可能触发假削顶，也污染开头）——实测修复后峰值 0.23，无削顶。

### 3. 电平计量（界面未改，数据先进状态）

采集回调里统计：**峰值、削顶百分比、当前使用声道**，经 `/api/status` 暴露：

```json
{"level":-38.2,"clip_pct":0.00,"peak":0.83,"ch_used":0}
```

同时每 2 秒检查一次，异常写进 DEBUG 日志（不弹窗）：

- `输入削顶 0.12%——请降低输入增益`
- `输入电平偏低 -58 dBFS（第 2 路）——建议提高发端音量或改用线路输入`

## 二、验证

新增 5 条单元测试（`cargo test -p cp16plus-audio`，全部通过）：

| 测试 | 断言 |
|---|---|
| `dc_block_kills_offset` | 喂常数 1.0，0.5 秒后残留 < 1e-3 |
| `dc_block_keeps_pilot` | 450 Hz 幅度损失 < 2% |
| `auto_picks_louder_channel` | 右路 4 倍响 → 选右路 |
| `mix_mode_averages` | 混音模式仍是 (L+R)/2 |
| `mono_passthrough` | 单声道直通 |

整机（`cargo test` 全量）14 项核心测试 + 5 项音频测试全绿。

## 三、请你这样验证

装 **B0.1.3**，然后做**同一段音频、三种输入**的对比（这是回答"差别到底在哪"的关键）：

| 组 | 做法 | 记录 |
|---|---|---|
| A | 文件回放（基准） | 已知 ~24 字 |
| B | 声音设置 → 录制 → 显示禁用设备 → 启用「立体声混音」，选它当输入，同时播放同一 WAV | 若接近 A → 设备/DSP 是元凶 |
| C | 扬声器外放 + 麦克风（你现在的做法） | 若明显低于 B → 声学在吃信号 |

每组跑完看一眼 `/api/status` 的 `clip_pct`、`level`、`ch_used`，以及 DEBUG 里有没有电平告警。

如果想用旧的混音行为对照，把地址里的 `channel=auto` 改成 `channel=mix` 即可。

## 四、下一步（等你这轮结果）

- 若 B 接近 A、C 明显差 → 问题在声学/电平，做"逐音自适应门限 + 行内去倾斜"（方案第 2 层 2、3 项）；
- 若 B 也差 → 设备/DSP 在破坏信号（降噪/AGC），先定位是哪一项；
- 若三组差不多但仍只有 18 字 → 是段/行相位问题，做"行相位扫描"（方案第 2 层第 1 项）。

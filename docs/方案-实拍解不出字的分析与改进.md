## 三、为什么"原始瀑布看得很清楚，主界面却不出字"

### 先说一个实测结论（本轮做的对照实验）

拿发行包里的 25 字示例，人为劣化后送进同一条解码链（`/api/decode` 回放，统计 `cells`）：

| 条件 | 解出字数 |
|---|---|
| 原始 | **24 / 25** |
| 加噪到 SNR 20 dB | 18 |
| 加噪到 SNR 15 dB | 18 |
| 加噪到 SNR 10 dB | 18 |
| 0.25 s 混响 + SNR 15 dB | 18 |
| 强行 AGC（每 100 ms 归一化到固定峰值） | 24 |

三个数字值得记住：**24 → 18 → 18 → 18**。噪声从 20 dB 一路降到 10 dB，字数一点没再掉，
说明 18 这个数不是噪声造成的，而是**结构性的 6 个字丢失**（很可能与段边界/行相位有关）。
你现场 10–20 字也在这个区间。

**结论：现有解调对噪声和混响并不敏感**——SNR 掉到 10 dB 仍有 18 字，混响 0.25 s 也是 18 字。
**所以"降噪"不是本轮的突破口**，问题在下面两处之一：

1. **解出来的行与显示出来的行不是同一批**（段/行相位、盲锁段与突发段并存）；
2. **显示层把本来有对比的行渲染成了糊块**（归一化/门限问题）——你截图里那块"只占左侧
   22% 宽、其余全黑"的紫色，更像是**每行只有前 3–4 个音有值**，而不是"字太淡"）。

这也解释了为什么"原始瀑布清楚、主界面没字"能同时成立：它们看的是两份数据——
原始瀑布用泵里的 48 kHz 块现算，主界面用的是**段内解调出来的 16 个音**。

### 两者的要求确实不同

| | 原始瀑布 | 主界面解调 |
|---|---|---|
| 数据 | 512 个 7.8 Hz 分辨 bin，逐帧现算 | 16 个音 → 一行 → 必须判 0/1 |
| 容错 | 峰值比底噪高 5–10 dB 就能看出笔画 | 需要每音**互相之间**分得开 |
| 时间 | 20 ms 一行，可以跨行连看 | 一行 80 ms 必须自己站得住 |


再叠加三个现实因素：

1. **音间隔只有 25 Hz，行长 80 ms** → 频率分辨 12.5 Hz，理论上够，但余量只有 2 倍。
2. **房间混响 20–40 ms**：上一个音的尾巴会压到下一个音上，麦克风拾音尤其明显。
3. **麦克风频响 + AGC**：Windows 默认可能开了"麦克风增强/自动增益"，它会把强弱差压平——
   而 CP16+ 的信息**全在强弱差里**。这是最容易踩、也最容易被忽略的坑。

所以"看得见 ≠ 解得出"。你看到的清楚笔画，是眼睛在替算法做积分。

## 五、工程上的改进方案（四层，按性价比排序）

### 第 1 层：诊断闭环（0.5 天，必须先做）

- 行环形缓冲 64 → **400 行**（32 秒）；
- 保留**最近 30 秒 8 kHz 单声道 PCM**（480 KB，导出时 base64）；
- 记录最近 16 个字符的位图与置信度；
- 支持"预期文本"手填，便于自动比对（给出正确字数/错字数）。

> 验收：你导一次包，我在本地离线复算，能准确说出"每个音的 SNR 是多少、哪几个音判错"。

### 第 2 层：解调与显示的一致性（1–2 天，治本）

根据上面的对照实验，**降噪不是首要矛盾**。优先做"能看见真相 + 行相位一致"：

1. **段/行相位自检（最高优先）**
   同一批音频里可能同时存在"突发段"和"盲锁段"。若盲锁段的行起点比真实行边界差半行，
   每个字都会被上下切一半 → 显示成条纹块，而 `cells` 计数照旧增加。
   做法：对每个段做一次**行相位扫描**（在 `[0, t_row)` 内试 8–16 个偏移），
   用"字形行的对比度（行内峰值/中位）"选最优相位；相位差超过 0.25 行就丢段重来。
2. **逐音自适应门限**
   用该音在**空白行**（字形行之间的留白）的功率作每个音自己的噪声参考，
   再定门限。现在的全局门限在通道有倾斜时会整列误判。
3. **行内去倾斜（tilt 校正）**
   用双导频（450 / 1250）的幅度差估一条 dB 斜率，把 16 个音按频率拉平——
   麦克风/扬声器的频响倾斜这一步能吃掉 3–6 dB 的损失。
4. **在线信道估计（做上面的兜底）**
   同步帧和 BCON 都是已知序列，用它们估每个音的复增益，对后续字符做均衡。
5. **采集端加 100 Hz 高通**（DC 那 +6 dB 就是它），省有效位数。

### 第 3 层：显示与提示（0.5 天）

- 主界面每行做**二值化 + 中值滤波**（去掉灰色糊块），置信度低的字用淡色；
- 机读层那一栏加"输入电平 / 每音 SNR / 削顶"三个小指标——
  这样"信号太弱"和"解错了"在界面上就能分开，不用每次发诊断包；
- 电平过低/削顶时直接给一句人话提示：“输入电平太低，建议提高发端音量或改用线路输入”。

### 第 4 层：采集方式（0.5 天，可能最省事）

工程上最立竿见影的往往不是算法，而是**换条音频路**：

- 麦克风拾音 → **线路输入**（对讲机/手机耳机口 → 声卡 Line-in/Mic-in，加衰减线）；
- 或者在软件里加"系统环回采集"（WASAPI loopback），直接把播放的声音抓进来，
  彻底绕开房间声学；
- 检查并**关闭 Windows 的"麦克风增强 / 自动增益 / 噪声抑制"**——
  这三项对 CP16+ 是破坏性的。

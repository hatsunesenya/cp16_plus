# 两条录音的对比分析：为什么 good 能解、bad 不能，以及怎么改才不依赖设备

> 本文只讲分析与改法。样本：`good.wav`（平板播放 → 手机录音）、`bad.wav`（平板播放 → 电脑麦克风）。
> 源文件都是发行包里的 `示例-长报文25字.wav`。

## 一、先量一下这两段录音到底差在哪

| | 采样率 | 声道 | 位深 | 时长 | RMS | 峰值 | 450 Hz | 1250 Hz | 字带（600–1300）中位 |
|---|---|---|---|---|---|---|---|---|---|
| 原始 WAV | 8000 | 1 | 16 | 38.9 s | −17.0 dBFS | 0.99 | −33.2 | −33.2 | −44.6 |
| good | 48000 | 2 | 24 | 35.8 s | −21.4 dBFS | 0.45 | −46.4 | −34.7 | −52.5 |
| bad | 44100 | 2 | 16 | 36.6 s | **−41.1 dBFS** | 0.08 | −61.2 | −60.4 | −71.8 |

- **bad 比 good 低 20 dB**，峰值只有 0.08；
- good 有明显倾斜（450 比 1250 低 12 dB），bad 平坦；
- 两者都没有削顶、没有直流。

关键发现：**这些差别并不是决定性的**——把 bad 整体放大 20 dB、或加噪到 SNR 6 dB，
解码结果几乎不变（见下"鲁棒性"一节）。所以问题不在电平，而在**解码器对"没有突发"的容忍度**。

## 二、真正的病灶：丢字的地方完全一样

用流式解码器（App 走的那条路）跑这两段录音，输出字符的时间点：

```
good/bad： 9.4s …→ 14.7s  （出 4 个字）
           15s ── 空 10 秒 ──→ 25s  （从这里才继续出字）
```

再看 burst 检测结果（`CP16P_DEBUG=1`）：

```
bursts: BCON @11.0s, BCON @22.9s, BCON @34.7s   （整段只有 3 个，HDR 一个都没有）
```

对照原始 WAV：HDR 秒解，BCON 每 8 个字符一个，24 个字一个不少。

**所以因果链是**：录音路径让控制信道（620 Hz DQPSK，符号 8 ms）大量误码 →
HDR/BCON 解不出 → 老逻辑"只有拿到突发才开段"就开不出段 →
中间十几秒音频没有任何段在跑 → 一个字都不出。
而原始瀑布图看的是另一套数据（频率能量），所以照样"看得见"。

### 老代码的两处硬伤

```rust
// ① 盲锁段只在"收到过同步帧"时才开
if self.sync.frames > 0 { ... }

// ② 而且只开一次：blind_opened 一置位，后面再也不开
if rows_have >= 2.0 && !self.blind_opened { ... }
```

也就是说：**突发解不出 = 整段音频没人解码**。这跟"设备好坏"无关，是设计缺陷。

## 三、改法（不动协议、不限制设备）

### 1. 盲锁段不再依赖突发/同步帧，也不只开一次

只要导频标定可用、前面还有 ≥2 行没解过的音频，就开一个盲锁段；
段收口后游标前移，可以一直开下去。

### 2. 开段前做行相位扫描

盲锁段不知道真实行边界在哪，差半个行就会把每个字上下各切一半。
现在在 `[0, t_row)` 内试 8 个偏移，用"行内峰值/中位"的对比度挑最好的一个；
对比度太低（纯噪声）就不开段，避免吐垃圾。

### 3. 突变还在未来时，先用盲锁把空档填上

老逻辑：拿到一个突发就立刻开段，哪怕这个突发在 7 秒之后 → 这 7 秒没人解码。
现在：下一个突发如果还在"当前音频之外"，先开盲锁段补空档，等音频走到突发再切过去。

### 4. 看门狗：段在跑却长期不出字，就放弃它

录音里常有误判的突发。段开着、行在解、但 4 秒（盲锁段 6 秒）没吐一个字，
说明起点或相位是错的 → 放弃、游标前移，交给盲锁重新对齐。

## 四、效果

| 样本 | 改动前 | 改动后 |
|---|---|---|
| 原始 WAV | 24 字 | **24 字**（不变） |
| good.wav | 12 字 | **22 字** |
| bad.wav | 12 字 | **21 字** |

App 里走 `/api/decode`（流式、实时节奏）复核：good 22、bad 21，与离线一致。

### 鲁棒性（以 bad.wav 为底）

| 条件 | 字数 |
|---|---|
| 原始（RMS −41 dBFS） | 21 |
| 再衰减 10 dB | 21 |
| 再衰减 20 dB | 15 |
| 加噪到 SNR 6 dB | 21 |

电平在 −10 dB 以内完全不影响；噪声 6 dB 也不影响。

## 五、还没解决的

1. **HDR 解不出**：两段录音的 HDR（报文开头的呼叫/网格）都失败，`机读层` 因此为空。
   原因是 DQPSK 在声学路径下（混响 20–50 ms、符号 8 ms）误码严重。
   这不是本次改动的范围，下一步要么在发射端周期性重发 HDR，要么在接收端做多假设/信道估计。
2. **开头 1–2 个字**仍可能丢（录音从报文中间开始，属于正常损耗）。
3. −20 dB 这种极端低电平（16 bit 录音）仍有 15 字，需要更稳的软判决与逐音门限。
